# 07 — Gap Analysis

Presented without advocacy, grouped by type.

## 1. Public documentation/implementation gaps

Five of eight surveyed public repositories (`mocka-runtime`, `mocka-outfield`, `mocka-public`, `mocka-civilization`, `mocka-external-brain`) contain architecture and protocol documentation with no corresponding code in that repository. Three repositories' README "Quick Start" sections reference scripts that do not exist in the tracked repository (`mocka-public`: `verify_chain.py`; `mocka-transparency`: `verify_chain.py`, `verify_all.py`; `mocka-outfield`: a referenced log file path). **This is the single most significant finding for any external reviewer relying only on Layer 1 (Public) evidence**: a reviewer who read READMEs without attempting to run the advertised commands would likely overstate MoCKA's demonstrated capability.

> **Independent Audit correction (2026-07-11):** `mocka-external-brain`'s inclusion in the "no corresponding code" list above is defensible in a narrow code-only sense (the tracked artifact is data, not executable code), but two related claims made elsewhere in this project about this same repository are factually **incorrect**. Direct verification against `origin/main` found `logs/bus/events.csv` (real, populated, 3,835 bytes) and two round-transcript files under `logs/bus/rounds/`, all tracked and containing genuine Feb-2026 deliberation records in the exact schema the README describes (`event_id`, `round_id`, `motion`, `actor`, `parent_event_id`, `evidence_ref`, `hash`). This directly contradicts `appendix/evidence/full_repository_survey.md` §6, which states this file "does not exist," and `03_RUNTIME_GOVERNANCE_SPECIFICATION.md` §3 (as originally written), which stated "no schema or bus implementation in-repository." `mocka-external-brain` should be counted as **Partially Implemented (Layer 1)** with real (if limited) protocol-execution data, not as a repository with a broken Quick Start reference. See `appendix/INDEPENDENT_AUDIT_REPORT.md` Finding 1 for full detail; `appendix/evidence/full_repository_survey.md` has been corrected accordingly.

## 2. Internal-vs-public visibility gap

The internal Decision Ledger and Integrity Classification Ledger (`03_RUNTIME_GOVERNANCE_SPECIFICATION.md` §4) show materially more governance activity, self-correction, and explicit anti-autonomy discipline than is visible from public repositories alone. This cuts both ways: it means the Layer 1 evidence base understates MoCKA's actual operational governance maturity, but it also means an external reviewer — including NIST — currently has no way to confirm any of it without the project owner granting direct access. A report relying solely on Layer 1 evidence would be materially incomplete in the favorable direction; a report relying solely on Layer 2 evidence would be unverifiable and inappropriate for institutional citation. This project's layered structure (`04_REQUIREMENT_MAPPING.md`, `05_COMPARATIVE_ANALYSIS.md`) is a direct response to that tension, per the project owner's explicit instruction and the Evidence Policy in `00_PROJECT_CHARTER.md`.

## 3. Confirmed open internal risk (disclosed per no-advocacy principle)

Integrity Classification record `IC_20260708_004` (Open, internal) documents an execution path where an audit-seal action can proceed after only an automated policy check, without a code-enforced additional human-approval step, despite the automated check's own documentation stating that mechanical approval is not equivalent to human approval. This is the most significant single Gap Analysis item in this project. Its disclosure here, alongside the internal record of the *process that found it*, is itself evidence of a functioning self-audit capability — but the underlying gap is real, unresolved, and should not be understated.

## 4. Scope mismatches against NIST's illustrative framing

NIST's Concept Note examples (`02_NIST_REQUIREMENT_ANALYSIS.md` §2) are drawn substantially from OT/ICS/physical-infrastructure contexts (plant monitoring, digital twins, robots, physics-informed control). MoCKA's governance mechanisms, as evidenced, are built for and operate on a **software/AI-collaboration governance domain** (event ledgers, Decision Ledgers, multi-agent chat coordination) rather than physical OT/ICS control systems. Several requirement mappings in `04_REQUIREMENT_MAPPING.md` (notably R5 adversarial robustness, R11 drift) show real MoCKA capability addressing a *related* problem in a *different* domain than NIST's illustrative examples target. This is a scope observation, not a criticism of either party — the NIST profile does not yet exist in a form specific enough to confirm whether it will extend to this domain at all.

## 6. Self-classification inconsistency in `MOCKA_OVERVIEW.json` (newly discovered during R01 Phase 1 review)

`data/MOCKA_OVERVIEW.json` is tracked and public on `origin/main` of the `MoCKA` repository (last modified 2026-07-08, commit `b7439e26d`). The file's own `meta.classification` field reads `"PRIVATE - ローカルのみ管理"` ("PRIVATE — local management only"). The file is nonetheless committed to a public GitHub repository and has been since at least that commit. This is a genuine, previously undocumented discrepancy between MoCKA's internal self-description and its actual public exposure — disclosed here rather than omitted, consistent with this project's no-advocacy principle.

Two related, practical consequences follow directly from this: (1) this project's own v1.0 draft misclassified `MOCKA_OVERVIEW.json` and the TODO Register as Layer 2 (Internal, Not Publicly Verifiable) when they are in fact Layer 1 (Public); this was caught and corrected only during the Phase 1 re-investigation triggered by R01's review requirement to catalogue "Living Context" explicitly (`appendix/REVIEW_LOG.md`). (2) Any other content the project owner intends to keep private should not be assumed private on the strength of an in-file `classification` label alone — actual `git ls-tree`/`gh` verification against `origin/main` is the only reliable check, as this project's own initial error demonstrates.

## 9. CI Verification Failure — Root Cause Analysis: `m-sirius-k/m-sirius-k`'s `portal_verify.py` (Corrective Action Phase, 2026-07-11)

Recorded as an independent Gap per explicit R01 instruction, separate from the general repository-coverage gap in §8. Full primary-source detail (file contents, exact commands) is in `appendix/evidence/REPOSITORY_SURVEY_ADDENDUM_m-sirius-k.md`; this section summarizes cause, impact, reproduction, and remediation options.

**Cause — two independent defects, either one sufficient to fail the check alone:**

1. `tools/portal_verify.py` hardcodes the path `DEMO_ARENA.md` for its second required document. The repository's tracked file is named `VERIFICATION_ARENA.md`. `Path("DEMO_ARENA.md").read_text()` raises `FileNotFoundError`, which the script catches and reports as `FAIL: DEMO_ARENA not found`, then exits 1.
2. Independently of (1): the script also requires `README.md` to contain six exact heading substrings (`# Architecture`, `# Repositories`, `# Research Workflow`, `# Technical Backbone`, `# Verification Architecture`, `# Quick Demo`). Direct comparison of the live `README.md` against this list found **3 of 6 missing**: `# Repositories`, `# Verification Architecture` (the README has a differently-worded `### Research Gate Verification` instead), and `# Quick Demo` (absent entirely). Even if defect (1) were fixed in isolation (e.g., by renaming `VERIFICATION_ARENA.md`), the check would still fail on the README side alone.

A third, related but evidentially distinct discrepancy: the README separately claims `RESEARCH_RUN OK — Verification checks executed: 20 — All verification checks passed`, describing a 20-check "Research Gate" framework documented in prose in `docs/verification/system_integrity.md`. No script, workflow, or executable artifact implementing any of those 20 named checks exists anywhere in the repository — only the unrelated, 2-check `portal_verify.py` is real and running. This claim is therefore **unsubstantiated by any evidence found in this repository**, independent of the CI failure itself.

A repository artifact of uncertain purpose, `testleadME.md`, already satisfies 5 of the 6 required README headings verbatim but is not named `README.md` and is not referenced by the workflow. Its relationship to the failure (abandoned fix attempt vs. unrelated draft vs. something else) is **Evidence Pending** — this project has no basis to infer authorial intent from file content alone.

**Impact scope:** `.github/workflows/portal_verify.yml` triggers on every push to `main` touching `README.md`, `DEMO_ARENA.md`, `tools/**`, or the workflow file itself. All 12 recorded runs (2026-03-06 to 2026-03-22) failed. `VERIFICATION_ARENA.md` itself — the repository's own public-facing verification index — directs external readers to this exact workflow's run history as "public execution evidence" and tells them to look for `RESULT: PASS` / `RESULT: FAIL`. Any external party who follows the repository's own stated verification instructions will observe only failures, which directly contradicts the separate "all verification checks passed" claim describing the (unimplemented) 20-check framework. The practical impact is reputational/evidentiary rather than operational: no downstream MoCKA system depends on this specific check succeeding, as far as this project's scope could determine.

**Reproduction steps:**
1. Checkout `m-sirius-k/m-sirius-k` at `main` (any commit since the workflow was introduced).
2. Run `python tools/portal_verify.py` from the repository root, or trigger the GitHub Actions workflow (`workflow_dispatch` or a push touching a watched path).
3. The script attempts to read `DEMO_ARENA.md`; this raises `FileNotFoundError` (actual file is `VERIFICATION_ARENA.md`) → prints `FAIL: DEMO_ARENA not found: <path>` → exits 1.
4. Independently, even with a correctly-named/present `DEMO_ARENA.md` substituted, `check_headings("README.md", ..., REQUIRED_README_HEADINGS)` against the live README text returns 3 missing headings → also prints `FAIL`.
5. Either failure alone is sufficient for `RESULT: FAIL` and a non-zero exit code, which the CI job surfaces as `conclusion: "failure"`.

**Remediation options (presented for project-owner decision; this project does not prescribe one):**

- **Option A — conform the content to the checker:** rename/create `DEMO_ARENA.md` with the six required headings (`testleadME.md`'s existing heading set could plausibly be adapted for this, or for `README.md` directly), and add the three missing headings to `README.md`.
- **Option B — conform the checker to the content:** update `tools/portal_verify.py`'s `REQUIRED_ARENA_HEADINGS`/filename constant and `REQUIRED_README_HEADINGS` to match `VERIFICATION_ARENA.md`'s and `README.md`'s actual, apparently-intentional structure.
- **Option C — retire the check:** if this verification concept has been superseded by newer MoCKA verification mechanisms (e.g., the Ed25519 audit chain and `verify_all.py` in the `MoCKA` core repository), consider deprecating `portal_verify.yml` rather than leaving a permanently-failing public CI badge on the org-profile repository, which is often the first thing an external visitor sees.
- In any case: separately reconcile or remove the unsubstantiated "20 verification checks passed" claim, since no corresponding implementation was found in this repository under any of the three options above.

**Status: Open.** This project has recorded the finding and remediation options per the no-advocacy principle; implementing any remediation is a decision and action for the project owner, not this audit.
